Section 1: Architecture Blueprint

Distributed Rate Limiting with Redis Token Bucket & Edge Gateways

At high concurrency (50,000+ RPS), local in-memory rate limiting fails across multi-instance clusters. By offloading token bucket evaluation to Redis via atomic Lua scripts, we achieve single-digit millisecond latency while guarding against distributed DDoS and rogue scrapers.

📊 SYSTEM DESIGN TOPOLOGY: DISTRIBUTED RATE LIMITER 📱 Mobile Responsive
[ TIER 1: CLIENT INGRESS ] HTTPS / HTTP/2
Distributed Clients (Web & Mobile Apps)
50,000+ RPS burst ingress. Attaches idempotency key & JWT authorization bearer token.
↓ [ AWS ALB: Layer 7 Routing & TLS Termination (P99 < 1.8ms) ]
[ TIER 2: EDGE RATE LIMITER GATEWAY ] EXPRESS / FASTIFY
Node.js API Gateway & Rate Limit Middleware
Extracts client IP / user ID. Dispatches atomic Redis Lua script EVALSHA for token bucket.
↓ [ Atomic Token Bucket Evaluation in Redis Cluster ]
[ PATH A: TOKENS >= 1 (ALLOW 96.4%) ]
Node.js Microservices Cluster
Executes business logic, queries database read replicas & returns HTTP 200 OK.
[ PATH B: TOKENS < 1 (REJECT 3.6%) ]
HTTP 429 Too Many Requests
Instant early return with Retry-After: 60s header. Zero downstream database load.
↓ [ State Persistence & Replication ]
[ TIER 3: DISTRIBUTED STORAGE & EVENT LOG ] POSTGRESQL + KAFKA
Multi-Region Distributed Primary & Replication
Writes to primary with synchronous commit; asynchronous WAL replication to regional read replicas.

Notice how the architecture gracefully separates the high-velocity fast path (cached Redis in-memory lookup) from the slow path, protecting our primary relational databases from cascade outages during flash traffic spikes.

Section 2: Node.js Under The Hood

Microtasks, Macrotasks & Libuv Event Loop Phases

Understanding the order of execution between process.nextTick(), Promise microtasks, and Libuv event loop phases is the difference between an application that handles 50k RPS smoothly and one that suffers catastrophic event loop starvation.

📊 NODE.JS ENGINE STATE & EVENT LOOP EXECUTION FLOW 📱 Mobile Responsive
[ STAGE 1: V8 JIT COMPILER ] V8 ENGINE
V8 Synchronous Call Stack
Executes top-level synchronous JavaScript code until the call stack is completely empty.
↓ [ Synchronous Frame Finishes Execution ]
[ STAGE 2: HIGHEST PRIORITY MICROTASKS ] MICROTASKS
process.nextTick() & Promise.then() Queues
Drains completely between every tick and before Libuv advances to the next event loop phase.
↓ [ Microtask Queue Empties • Enters Libuv Event Loop ]
[ STAGE 3: LIBUV EVENT LOOP PHASES ] C++ LIBUV
Timers → Pending I/O → Poll → Check (setImmediate) → Close
Non-blocking OS asynchronous I/O multiplexed via epoll (Linux) / kqueue (macOS) / IOCP (Windows).
↓ [ CPU Intensive Tasks / Sync File I/O Offloaded ]
[ STAGE 4: OFF-THREAD WORKER POOL ] UV_THREADPOOL
Libuv Worker Thread Pool (crypto, zlib, fs, dns)
Pool of 4 OS threads handles synchronous blocking operations without choking the single JS main thread.

Always ensure asynchronous tasks never starve the event loop. Microtasks execute immediately after the current operation finishes, meaning an infinite recursive microtask loop will freeze the entire event loop tick cycle.
